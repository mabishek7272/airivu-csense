# 08 — API Guide

**Version:** 1.0
**Audience:** Anyone integrating with the CSense API — an internal frontend, a customer's
own automation, or a third-party integration using a scoped API key.

## Two APIs, two audiences

| | Tenant API | Admin API |
|---|---|---|
| Base path | `/api/v1/tenant/*`, `/api/v1/auth/*`, `/ws/v1/tenant/*` | `/api/v1/admin/*` |
| Who calls it | A tenant's own users (owner/member), or a scoped API key issued by that tenant | Platform staff |
| Interactive docs | `GET /api/v1/tenant/docs` | `GET /api/v1/admin/docs` |
| OpenAPI document | `GET /api/v1/tenant/openapi.json` | `GET /api/v1/admin/openapi.json` |

Both are real, live, auto-generated by FastAPI from the actual route definitions — never
a hand-maintained document that can drift from what the API actually does. Start there
for the full, current endpoint-by-endpoint reference; this guide covers the concepts
that don't fit in an OpenAPI document.

## Authentication

### Human sessions (JWT access + refresh)

```
POST /api/v1/auth/register   {organization_name, email, password, display_name}
POST /api/v1/auth/login      {email, password}  ->  {access_token, refresh_token, tenant_id, ...}
POST /api/v1/auth/refresh    {refresh_token}    ->  a new access_token
```

Send the access token as `Authorization: Bearer <token>` on every subsequent call.
Access tokens are short-lived (`JWT_ACCESS_TOKEN_TTL_SECONDS`); refresh before they
expire rather than re-authenticating with a password every time.

Tokens are audience-scoped (`csense-customer` vs `csense-platform`) — a customer token
will never be accepted on `/api/v1/admin/*`, and vice versa, enforced at decode time, not
just by which endpoints happen to check for which role.

### MFA / step-up

TOTP-based MFA is available on both sides (`/mfa/totp/enroll` → `/mfa/totp/confirm` →
ordinary login now asks for a code). A small set of high-risk actions (issuing/renewing
a license, on the admin side) additionally require a **recent step-up verification** —
`POST .../auth/mfa/verify` with a fresh code, valid for a few minutes — independent of
whether your session token itself is still valid. A `403 step_up_required` names exactly
which call to make.

### Scoped API keys (machine-to-machine)

A tenant owner can issue their own API keys for integrations, without giving out a human
password:

```
POST /api/v1/tenant/api-clients   {name, scopes: [...], site_scope_mode, rate_limit_per_minute}
```

`scopes` must be a subset of the issuing user's own permissions — a key can never be
issued more power than the person issuing it currently holds. The response's `api_key`
field (`csak_...`) is shown **exactly once**; only its prefix is ever stored or returned
again. Use it the same way as a human token:

```
Authorization: Bearer csak_...
```

Every API-key-authenticated call is rate-limited to the key's own configured
`rate_limit_per_minute` (a real, Redis-backed fixed-window limiter — expect up to ~2x
burst right at a minute boundary, a named, accepted tradeoff over a heavier sliding-
window scheme) and metered (`GET /api/v1/tenant/api-clients/{id}/usage`). A refused call
still counts toward usage — you paid for the request even when it was throttled.

Revoke a key immediately via `POST .../keys/{key_id}/revoke`; issue a fresh one via
`POST .../keys` without disturbing the client's other keys — rotation without a gap.

## Permissions (RBAC)

Every endpoint is gated by a `resource.action` permission code (e.g. `camera.read`,
`incident.close`, `webhook.manage`) attached to the caller's role at token-issuance time.
There is no implicit grant — a missing permission is always a deny ("deny wins", the same
rule for both human sessions and API keys). The full, current set of permission codes is
visible in `docs/07_OPERATIONS_MANUAL.md`'s admin sections and in each migration file
under `backend/migrations/versions/*_permissions.py`; there is no separate endpoint that
enumerates them today.

## Error shape

Every error response has the same shape (`csense_shared.errors.ProblemResponse`):

```json
{
  "code": "quota_exceeded",
  "message": "This tenant's camera limit (5) is already in use (5). ...",
  "details": {"limit_value": 5, "in_use": 5},
  "correlation_id": "c59e68aa-...",
  "retryable": false
}
```

`code` is a stable, machine-readable string — match on it, not on `message` (which is
meant for a human to read and may be reworded). `retryable: true` shows up on things like
rate-limit refusals; `details` carries whatever structured context the specific error
has (a quota limit, a retry-after duration).

Two authentication-adjacent error codes are deliberately identical regardless of the
actual cause (an unknown API key, a tampered one, or a revoked one all return the exact
same `401 api_client_unauthenticated`/`device_unauthenticated`) — this is intentional,
not a bug: distinguishing them would let someone probing with guessed credentials learn
which ones are close to real.

## Pagination and cursors

List endpoints that can return a lot of rows use a `cursor`/`limit` shape (e.g.
`GET /api/v1/tenant/incidents?limit=25&cursor=...`) — pass the previous response's own
`next_cursor` back to continue, rather than an offset (which drifts under concurrent
writes). Endpoints without this shape return everything in one response and are known,
by design, to be bounded in size (e.g. a tenant's own site list).

## Webhooks

A tenant can register a webhook endpoint to receive real event notifications:

```
POST /api/v1/tenant/webhooks   {name, url, event_filters: []}   # [] = all events
```

The response's `signing_secret` (`whsec_...`) is shown once — store it, and verify every
delivery against it the same way Stripe/GitHub webhooks work:

```
X-CSense-Signature: t=<unix timestamp>,v1=<hex hmac-sha256 of "t.body">
```

Recompute the HMAC over `f"{t}.{raw_body}"` using your stored secret; reject anything
where the signature doesn't match or `t` is outside a 5-minute tolerance window in either
direction (replay protection — a captured, replayed request becomes unverifiable once it
ages out of the window, no nonce store needed on the sending side).
`POST /api/v1/tenant/webhooks/{id}/test` sends a real, signed test payload on demand so
you can verify your receiver before relying on live events.

**Current scope, named honestly**: delivery is real and on-demand (the `/test` endpoint)
today; systemic automatic delivery triggered by every domain event across the whole
platform is a separate, larger wiring effort not yet built — see `CHECKLIST.md`.

## Idempotency

Mutating requests that might legitimately be retried (an edge device replaying a queued
detection after reconnecting, a client retrying after a timeout) should carry an
`Idempotency-Key` header where the endpoint supports it — a redelivered request with the
same key and the same logical content is recorded once, not duplicated. Detection
ingestion in particular is built around this from the ground up (edge devices are
expected to retry; the server is expected to deduplicate, not the device).

## Real-time

`GET /ws/v1/tenant/...` — a WebSocket for live incident/detection updates, authenticated
via a short-lived ticket (`csense_shared.security.ws_tickets`) rather than a bearer token
in the URL (a token in a URL ends up in logs and browser history; a single-use ticket
minted just before connecting does not carry the same risk).
